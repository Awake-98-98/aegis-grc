# M2 设计取舍：资产清单与威胁面

记录 M2 阶段做的决定，以及被放弃的做法。M3 开始做风险评分时会回看这份记录。

## 1. 资产挂在项目下，不挂在客户下

同一客户在不同项目里关注的资产范围不同。年度评估可能覆盖全部生产系统，而一次专项渗透只关心对外 Web 入口。若资产挂在客户下，第二个项目要么复用一张很长的资产表，要么另建一套，两种都不合适。

代价是同一台服务器在两个项目里会有两条记录。这在咨询场景里是可接受的：每条记录的分级和责任人可以不同，报告也按项目交付。

## 2. CIA 存 1–4，关键度与优先级分不落库

数据库只存 `confidentiality`、`integrity`、`availability` 三个整数，并用 `CHECK` 约束在 1–4。关键度与优先级分由模型属性计算：

- 关键度取三者最高档（4 → critical，3 → high，2 → medium，1 → low）
- 优先级分 `C×3 + I×2 + A×2`，范围 7–28

理由有两个。一是避免派生字段与源字段不一致，任何一次漏更新都会让报告和列表对不上。二是评分口径在 M3 很可能调整，落库后每次改口径都要写迁移回填。

代价是按关键度筛选要在 SQL 里展开成条件表达式。`_criticality_filter` 用 `or_`/`and_` 拼出四档条件，没有引入 `MAX(c,i,a)` 这类 SQLite 专有写法，迁移到 PostgreSQL 时不用改。

没有采用 5×5 矩阵里的 1–5 级，是因为 CIA 赋值在咨询实务里通常只看四档：可忽略、有限、严重、致命。多一级只会让访谈对象犹豫。

## 3. 威胁目录按项目维护

最初考虑做一份全局威胁库，所有项目共享。放弃的原因是威胁的措辞与颗粒度随项目变化很大：银行项目会把“钓鱼邮件”拆成“鱼叉邮件投递”“凭据填充”“OAuth 授权滥用”，制造企业只写一条“钓鱼邮件”。强行统一会让顾问为了复用而写不准确的条目。

项目内威胁名称唯一，跨项目允许重名。项目复制（M6 计划）时整份目录一起复制，届时再考虑抽取模板。

## 4. 配对表是 M3 的评分单元

`asset_threats` 不只是一个多对多关联表，它承载 `vulnerability`（具体薄弱点）与 `exposure`（暴露程度）。M3 对一对资产-威胁打分时，输入是资产的影响等级加上这里的暴露程度，输出是风险值。

因此配对表按“资产 + 威胁”唯一，不允许同一对重复登记。若同一对存在两个不同薄弱点，正确做法是拆成两条威胁（例如“未装补丁”和“弱口令”），而不是在一条配对里堆两段文字。

## 5. 资产同时受两个唯一约束

- `(engagement_id, code)`：编号不能重复
- `(engagement_id, name)`：同一项目内资产名称不能重复

名称唯一是为了让导入可以幂等，也让报告里的资产清单不会出现两个“核心交换机”而无法区分。副作用是确实存在两台同名设备的场景，此时顾问需要写成“核心交换机（A 机房）”与“核心交换机（B 机房）”。

有人会问为什么编号不直接做主键。编号是给人看的，可能因为合并项目而重排；UUID 主键不随业务变化，关联表也更安全。

## 6. CSV 导入：部分成功、按名称去重

导入不追求整批原子性。逐行校验，合法行入库，非法行记入 `errors`，同名行记入 `skipped_rows`，最后返回三类计数。理由：

- 顾问从客户那里拿到的 Excel 通常有几十行脏数据，整批回滚等于让人一行行找错；
- 重复导入是常态（客户补了几行），按名称跳过比报错更符合预期；
- 一次导入写一条汇总审计，而不是每行一条，避免审计表被导入噪音淹没。

编码按 `utf-8-sig` → `utf-8` → `gb18030` 顺序尝试。Windows 上导出的 CSV 常带 BOM 或 GBK 编码，先试 BOM 变体能省掉很多“第一列表头多了个问号”的问题。

表头匹配去掉大小写、空格、下划线、连字符后比较，所以 `Asset Type`、`asset_type`、`类型` 都能落到同一列。取值也允许中文别名，因为填写表格的人不会记得枚举名。

单次上限 1000 行。超过时停止处理并在 `errors` 里说明，不静默截断。

没有做的部分：导入预览与回滚。预览需要暂存整批数据，回滚需要给每行打批次标记，两者都会让 M2 的表结构复杂化。当前先保证“导入结果可读”，如果实际使用中误导入频繁，再在 M6 加批次回滚。

## 7. 删除是级联，不设归档

客户与项目采用归档，因为它们是长期资产，历史报告要能追溯。资产与威胁不同：它们是某个项目的工作底稿，项目状态一旦进入 `reporting`，资产清单已经冻结在报告里，数据库里的记录只是过程数据。

因此删除资产会级联删除配对，删除威胁会级联删除配对，删除项目会级联删除资产与威胁。审计事件全部保留，删除动作本身也有记录，追溯不受影响。

## 8. 放弃的方案

- **资产树形层级**（业务系统 → 子系统 → 组件）：ISO 27005 的分层描述里确实有这层，但咨询交付物通常只到“系统”这一粒度，加层级会让录入成本翻倍。类别字段加自由文本位置已经够用。
- **JSON 导入**：CSV 是客户能提供的唯一通用格式。JSON 只在内部脚本里有用，而内部脚本可以直接调 API。
- **资产变更历史表**：审计事件已经记录前后快照，单独建历史表是重复存储。审计查询按实体过滤即可得到变更轨迹。
- **把威胁分类做成可维护字典表**：当前 7 个分类覆盖常见场景，字典表会带来一层配置界面和权限，收益不足。若 M3 需要按分类做统计口径，再改为枚举常量。

## 9. 尚未落地

- 威胁与控制的映射（M4）
- 批量修改分级（当前只能逐条编辑）
- 资产导入的字段级错误定位到列名而不是表头原文（现在返回 canonical 字段名，够用但不便直接对照 Excel）
