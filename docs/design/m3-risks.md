# M3 设计取舍：评估批次与风险登记册

记录 M3 阶段做的决定，以及被放弃的做法。M4 做控制库时会在此基础上补控制覆盖。

## 1. 批次是版本单元，不是一张长期登记表

一个项目可以有多份评估：初评、整改后复评、年度复评。如果只维护一张随改随变的登记表，报告里引用的数字第二天就对不上；如果每次都复制整张表，又很难说清哪两份是同一份评估的前后版本。

因此把"评估批次"作为一等对象（编号 `RA-0001`），风险项挂在批次下。批次有两种状态：

- `draft`：可增删改评分项，也可以改标题、评估人、摘要；
- `issued`：签发后冻结，风险项不能增删改，批次信息不能改，不能重复签发。

冻结不是靠界面隐藏按钮，而是在服务层抛 `StateTransition`（HTTP 409，`AEG-4001`）。Web 与 REST 都走同一处判断。

签发要求至少一条风险项。空批次签发没有意义，而且会让对比页出现一份全是"移除"的结果。

## 2. 分值不落库

数据库只存两套 L/I：`likelihood`/`impact` 与 `residual_likelihood`/`residual_impact`，都在 1–5。分值、等级、降幅都是 `RiskItem` 的派生属性：

- `inherent_score = likelihood × impact`
- `residual_score = residual_likelihood × residual_impact`
- `reduction = inherent_score - residual_score`
- 等级按分值查表：1–4 低、5–9 中、10–15 高、16–25 严重

这与 M2 不存优先级分是同一个理由：派生字段一旦落库就可能与源字段不一致。矩阵分档以后若要调整（例如把 9 划到高档），只改 `aegis/risk/matrix.py` 一处即可，历史数据自动按新口径重算。代价是列表排序和按分档筛选要展开成 `likelihood * impact` 的表达式，目前数据量下没有性能问题。

排序用 `ORDER BY (likelihood * impact) DESC`，没有在 Python 里排，因为分页在 SQL 侧完成。等出现慢查询再考虑加生成列。

## 3. 残余默认等于固有

新增评分时只填 L/I，残余两项省略即复制固有值。理由是从操作顺序看，顾问先把风险评出来，写完处置理由再回头调残余；强制填两套数字会让表单变长，也容易出现"残余大于固有"这种笔误。

服务层没有禁止残余高于固有。现实中处置引入新风险、或评估口径变化，都可能让残余升高，强行拦截会逼人改固有值来绕过。对比页会把"残余升高"单独计数，让这种情况可见。

## 4. 风险项存资产与威胁快照

`risk_items` 除了外键 `asset_id`、`threat_id`，还存 `asset_code`、`asset_name`、`threat_code`、`threat_name` 四个快照字段。外键是 `ON DELETE SET NULL`。

两个后果：

- 资产或威胁被删除后，已签发的登记册仍然能读出"哪台设备、哪种威胁"，导出 CSV 不会出现空行；
- 资产改名不影响历史批次，报告仍显示评估当时的名称。

如果只存外键，删除资产会连带让历史报告缺项；如果只存名称，又无法从风险项跳回资产页。两者都留，各取所需。

## 5. 对比按编号匹配，不按主键

两份批次的逐项对比以 `(asset_code, threat_code)` 作为键。没有用 `(asset_id, threat_id)`，原因有两个：

一是资产改名或重新导入后主键可能变化，按主键会把同一条风险识别成"移除 + 新增"；二是快照编号本来就稳定，而且与人读报告时看到的编号一致。

对比结果分四类：新增、移除、变化、未变。比较的是两套 L/I 与处置策略；只要有一项不同就算"变化"。另外统计残余分升高与降低的条数，供汇总页展示。

对比允许任选同项目的另一批次，不要求基线一定更早。顾问有时会拿旧批次和新批次反着看，限制先后顺序只会增加一次点击。

## 6. 风险偏好只有一个阈值

项目级设置 `max_acceptable_score`，默认 9。风险项残余分高于阈值即计为"超出偏好"。

没有做按类别、按资产、按业务线的分级偏好。真实咨询里确实存在"核心系统容忍 4 分、办公系统容忍 12 分"的做法，但它需要一张偏好矩阵和一套匹配规则，而当前阶段最常用的问题是"还有几条超出偏好"，单一阈值已经能回答。等 M6 做指标看板时若确有需要，再把偏好扩展成按资产关键度分档。

偏好记录按项目唯一，用 upsert 写入。审计事件挂在 `engagement` 实体上，因为偏好属于项目属性，而不是某个批次。

## 7. 评分入口是已配对的资产-威胁

新增风险项只能从 `asset_threats` 里选，必须属于同一项目，且同一批次内不能重复评分同一对。

这延续了 M2 的判断：配对表承载薄弱点与暴露程度，是评分的自然单元。允许直接选资产加威胁会导致同一对在配对表和风险表里各存一份关系，删除时难以保持一致。

已配对的资产-威胁在详情页以"未评分"列表展示，避免顾问忘记某些配对。这个列表由路由层计算，不进服务层接口。

## 8. 放弃的方案

- **加权评分公式**（`L × I × 资产关键度系数`）：会让分值超出 1–25，矩阵失去直观性，而且权重本身需要一套治理流程。当前用 5×5 原值，关键度留给报告叙述。
- **逐条风险的历史表**：审计事件已经记录每次 L/I 与处置的前后值，单独建历史表是重复存储。需要轨迹时按 `entity_id` 查审计即可。
- **自动为所有配对生成评分项**：看似省事，但会把大量"已识别但暂不评估"的配对强行赋一个默认分，污染统计。改为详情页提示未评分数量。
- **按资产类别设偏好**：见第 6 节，当前收益不足。
- **批次签发后允许"撤销签发"**：会让已交付报告的数字失效，且撤销权限难以界定。要修正就新建批次。
- **把矩阵分档做成可配置项**：分档是方法论的一部分，不同项目用不同分档会让跨项目汇总失去可比性。固定在代码里，改口径走版本发布。
