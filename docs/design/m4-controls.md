# M4 设计取舍：控制库与合规映射

记录 M4 阶段做的决定，以及被放弃的做法。M5 做整改与证据时会引用这里的控制项与映射关系。

## 1. 框架目录是全局参考数据

`control_frameworks` 与 `controls` 不挂项目，由迁移 `m0004_controls` 一次性写入，主键使用稳定字符串（`fw-iso27001-2022`、`iso-a5-1`、`nist-gv-oc`、`mlps-pe-01`）。

三个理由：

- 标准条目对所有客户、所有项目相同，挂项目会重复存储并产生版本分叉；
- 稳定主键让测试、CLI 和演示数据可以直接按编号引用，不必先查名称；
- 目录只读，避免在界面里把"标准要求"改成另一句话，导致跨项目统计失去可比性。

代价是升级目录只能新增迁移，不能通过页面维护。当前三套框架都属于外部发布物，本来也不该由咨询方改写。

## 2. 三套框架的条目口径

| 框架 | 口径 | 条目数 |
|---|---|---|
| ISO/IEC 27001:2022 附录 A | 全部控制项，按组织、人员、物理、技术四个主题 | 93 |
| NIST CSF 2.0 | 六个功能下的类别，不展开子类 | 22 |
| 等保 2.0 安全通用要求 | 按 10 个安全域归纳的控制点 | 70 |

ISO 与 NIST 同时存中文标题和英文原题，等保只存中文。没有抄录标准正文，`guidance` 字段留空，供后续按项目补充实施说明。

NIST CSF 2.0 有 106 条子类。逐条纳入会让目录体积翻倍，而多数咨询交付按类别讨论差距；需要更细时再在控制项上挂子类，不必现在就把 106 行写进库。等保按控制点而不是按测评项拆分，同样是为了让映射粒度与风险项匹配。

## 3. SoA 按项目与框架惰性生成

适用性声明不是建项目时自动铺开，而是由顾问选择框架后显式生成。`soa_entries` 的唯一键是 `(engagement_id, control_id)`，生成动作只补缺失行，已有判断不覆盖。

这样做有三个后果：

- 项目只处理真正要用的框架，不会被另外两套目录的空行淹没；
- 重复点击生成不会重置已填的实施状态与理由；
- 92 项待办与 1 项不适用都能在同一张表里看到，不需要另建"排除清单"。

生成与编辑分离。生成是批量动作，记一条 `soa.generate` 审计；逐行修改记 `soa.update`，带修改前后的适用性、状态、理由与责任人。

## 4. 排除必须写理由

ISO 27001 要求 SoA 对每条控制项说明是否适用，不适用时给出理由。服务层把这个要求落成两条校验：

- `applicable=false` 且 `justification` 为空，返回 422 `AEG-2003`；
- `applicable=false` 时不允许标为 `in_progress` 或 `implemented`。

第二条看起来多余，但实际能挡住一类常见误操作：顾问先标了"已实施"，回头又取消适用，留下"不适用且已实施"的矛盾记录。汇总里单独统计"缺理由的不适用项"，让漏填可见。

没有把理由做成必填的长度下限。真实理由可能只有一句"由集团统一提供"，强行要求字数只会逼出凑字数的文字。

## 5. 映射挂在评分项上，随批次走

`risk_control_links` 关联 `risk_items` 而不是 `assets` 或 `asset_threats`。评分项是评估批次的快照，带着当时的资产与威胁名称、固有与残余分值；控制映射讨论的是"这条风险由哪些控制承接"，落在这里语义最直接。

代价是新批次不会自动继承旧批次的映射。这是有意为之：复评时风险描述、分值或处置策略可能变化，自动继承会让新版风险凭空显示"已覆盖"。需要沿用时应由顾问在新批次里重新确认。批量复制映射留到 M5 的整改流程里做，届时可以带审批。

唯一键是 `(risk_item_id, control_id)`，同一条风险与同一控制只能建立一条映射；覆盖程度分 `full`、`partial`、`planned` 三档，用一列表达"完全承接、部分承接、计划承接"，没有拆成多张表。

## 6. 覆盖率有两个口径

框架覆盖率与风险覆盖率回答不同问题，不能混用：

- 框架覆盖率 = 已实施且适用的 SoA 条目 / 适用条目。不适用项不进分母，否则排除越多覆盖率越低。
- 风险覆盖率 = 至少有一条控制映射的评分项 / 当前批次评分项总数。映射条数不影响分子，一条风险挂三条控制仍只算一条已覆盖。

未覆盖风险清单直接由第二个口径得到，按 `risk_item_id` 反查没有映射的评分项。两个口径都在读取时计算，不落库，理由是映射和状态会被反复修改，存统计值必然出现与明细不一致。

## 7. 被否掉的做法

- **在界面维护控制目录**：标准条目应随版本冻结，允许编辑会让历史项目的 SoA 无法解释。
- **按资产映射控制**：同一资产可能对应多条风险，控制挂资产会把"这条风险是否被承接"变成推断，未覆盖清单也算不准。
- **按关键词自动映射**：控制标题与风险描述的词面重合度很低，自动结果需要逐条复核，反而增加工作量。
- **SoA 生成时做快照**：SoA 是活的工作文档，不是签发的登记册；快照会让每次改状态都要新建版本。
- **展开 NIST 106 条子类**：类别级已足够支撑差距讨论，子类会稀释覆盖率的分母。
- **复制 ISO 正文**：标准文本受版权保护，目录只保留编号、标题与自拟说明。

## 8. 已知缺口

- 控制目录没有导入与版本升级入口，新增框架要写迁移。
- SoA 没有"签发"或"冻结"状态，修改不留版本，只能从审计里回溯。
- 风险覆盖只按当前批次计算，没有跨批次趋势。
- 控制项与整改任务尚未关联，M5 落地后再补"控制未实施"到"整改任务"的转换。
- 未覆盖清单只按项目批次列出，没有按资产关键度或残余分排序的聚合视图。
