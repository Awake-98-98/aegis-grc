# M5 设计取舍：整改计划与证据工作流

记录 M5 阶段做的决定。M3 的风险登记册说明"哪里有问题"，M4 的 SoA 说明"应该由哪些控制承接"，M5 把结论落成有人负责、有截止日期、有证据的整改任务。

## 1. 整改任务是操作单元

`remediation_tasks` 挂在项目下，编号 `RT-0001` 项目内自增。任务不直接等于评分项，也不直接等于控制项：

- 一条严重风险可能拆成多个任务，例如先做网络分区、再做备份演练；
- 一个任务可以覆盖多条同类风险；
- 任务可以完全不来自评估，例如客户在访谈中提出的整改事项。

评分项与控制项都以可空外键挂在任务上，删除来源后任务仍然存在，只是失去回链。任务自己保存标题、说明、负责人、优先级、截止日期和备注，这些字段是整改过程的真实输入，不从别处派生。

## 2. 状态机只有四条边

```
open → in_progress / blocked / cancelled
in_progress → blocked / done / cancelled
blocked → in_progress / cancelled
done, cancelled 为终态
```

没有引入"待验收""已关闭"等更多状态。咨询项目里的整改跟踪通常只关心"有没有开始、是否卡住、是否完成"，状态越多，更新越不及时。完成时写入 `completed_at`，回退到进行中会被拒绝。

非法流转返回 409 `AEG-4001`，与项目状态机共用同一错误码。删除只对 `open` 或 `cancelled` 开放，避免删除正在实施或已完成的任务，把历史抹掉。

## 3. 风险快照随任务保存

从评分项"转整改"时，服务把资产编号、威胁编号和残余分拼成 `risk_snapshot`，例如 `AST-0001 × THR-0002 残余 12`。任务详情直接展示这段文本，不再要求读者回到某个评估批次。

这样做的好处是任务跨批次可读：复评时资产改名、评分项被删或批次被新版本取代，任务仍然说明得清来源。代价是快照不会自动更新。残余分后来变了，任务里的数字仍是创建时的值；需要新数字时应新建任务或手工改标题，而不是让历史任务悄悄漂移。

快照只存文本，没有拆成三个独立列。当前只有展示需求，拆列会让表结构跟着评估字段变化，而文本拼接足够满足追溯。

## 4. 证据按内容寻址存放

证据文件不存进 SQLite，而是写到 `<home>/evidence/<sha256[:2]>/<sha256>`。数据库只保存摘要、文件名、类型、大小和上传人。

三个后果：

- 同一文件在多个任务间共享一份物理副本，复制项目或重复上传不会让数据目录膨胀；
- 摘要本身就是完整性校验，下载时可以直接比对；
- 备份数据目录等同于备份全部证据，不需要额外导出二进制字段。

写入先落在同目录的临时文件，`os.replace` 原子替换。读取方不会看到写了一半的文件，进程中断最多留下一个临时文件，不会污染正式摘要路径。

## 5. 上传幂等，删除看引用

同一个任务重复上传相同内容，服务直接返回已有记录，`created=false`，不写第二行。唯一键是 `(remediation_task_id, sha256)`，把幂等约束交给数据库。

删除分两层：

- 删除证据记录时，先删行，再统计同一摘要还有没有其他行；
- 没有其他引用才删除物理文件。两个任务共用一份文件时，删掉一个任务不会让另一个任务的证据失效。

删除整改任务时，数据库级联删除它的证据行，服务再按摘要检查并清理孤立文件。没有做后台垃圾回收；在当前规模下，显式清理比定时任务更容易解释。

单个文件上限 10 MiB。上限在服务层检查，Web 与 API 共用同一条规则。证据没有版本或审批流，谁上传、何时上传由审计轨迹回答。

## 6. 逾期按日期与终态计算

逾期定义只有一句：`due_date < 今天` 且状态不是 `done` 或 `cancelled`。

没有引入"宽限期"或"按优先级调整"的口径。逾期是提醒，不是考核；口径越简单，团队越容易对同一张清单达成一致。汇总同时给出未来 7 天内到期的数量，让"即将逾期"和"已经逾期"分开显示。

日期比较使用服务器本地日期。系统不处理跨时区团队，所有日期都是咨询项目所在时区的自然日。

## 7. 权限沿用两层读写

新增四个权限：`remediation:read/write`、`evidence:read/write`。consultant 全部拥有，viewer 只有读，admin 通过通配符拥有全部。

服务层仍然是唯一权限入口，Web 路由只负责校验 CSRF 后调用服务。Web 页面按权限隐藏表单，但隐藏不是安全边界；直接构造 POST 仍会被服务层拒绝并返回 403 `AEG-3002`。

证据下载同样要求 `evidence:read`，不复用静态文件目录。这样文件不会因为放在 `static/` 下而被匿名访问。

## 8. 被否掉的做法与已知缺口

被否掉的做法：

- **用评分项当待办**：一条风险往往对应多个动作，直接改评分项状态会污染已签发的登记册。
- **证据直接存 BLOB**：SQLite 文件会随附件膨胀，备份与迁移都变重，也无法跨任务去重。
- **按文件名去重**：同名不同内容很常见，按摘要去重才能保证内容一致。
- **上传即覆盖旧证据**：证据的价值在于留痕，覆盖会丢掉历史版本；需要新版本时应新增文件。
- **自动把未覆盖控制转成任务**：控制未实施不等于需要整改，是否立项应由顾问判断。

已知缺口：

- 任务没有评论、提醒或到期通知，状态更新依赖人工查看清单。
- 证据没有预览与文本抽取，只能下载后查看。
- 任务没有工时、成本或验收人字段，不能直接当项目计划使用。
- `control_id` 已建模但 Web 表单未提供选择器，目前只能通过 API 或 CLI 关联控制项。
- 证据删除没有软删除，误删只能从备份恢复。
